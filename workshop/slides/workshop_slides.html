Topic 01 · 15 min

What is a SQL AI Agent?

More than a single LLM call. A pipeline that turns a question into a row of data.

Topic 01 · prompt vs. agent

One LLM call ≠ a SQL AI agent.

✗ Just a prompt

Single LLM call

  • Returns text — not rows.
  • Doesn't know the schema.
  • Doesn't run the SQL.
  • If the SQL is broken, nothing tells us.
Useful as a step. Not a system.
✓ SQL AI agent

Orchestrated pipeline

  • Builds a prompt that includes the schema.
  • Calls the LLM, then parses the response.
  • Runs the query against the database.
  • Hands rows back to the user.
One LLM call is one step inside the loop.

Topic 03 · 12 min

Context is everything.

The cheapest, biggest lever on agent quality.

Topic 03 · the claim

"

The same model with better context beats a bigger model with worse context.

Most agent failures aren't reasoning failures. They're context gaps.

Topic 03 · three context layers

Three layers, one prompt.

An LLM only knows what we put in the prompt. Schema, business rules, prior turns — none of it is implicit.

Topic 03 · layer 1

Schema + distinct values.

1

What it is

The structural description of the table. Schema is always-on. Distinct values is opt-in: it tells the model that "Activity Type Code" holds 'Deplaned', 'Enplaned', 'Thru / Transit' — not 'arrival' or 'departure', which is what an LLM will guess otherwise.

How it's wired

get_tbl_attr + get_character_distinct_values in sql_ai_agent/db_handler.py. Formatted by format_distinct_values_for_prompt and appended to additional_context.

Sidebar · Include Distinct Character Values

Topic 03 · layer 2

Skills — the domain knowledge file.

2

What it is

A markdown file under skills/ that encodes what a human analyst knows but a generic LLM doesn't: column meanings (Deplaned=arrival), business rules (exclude transit, use Operating Airline), query patterns, percentage/growth math, common pitfalls.

How it's wired

SkillManager.load_skill(...) in sql_ai_agent/skill_manager.py. SqlAgent.__init__ tries <tbl_name>, <tbl_name>_context, sfo_<tbl_name>_context. For us: skills/sfo_air_traffic_context.md (~250 lines).

Code-only today (no sidebar toggle)

Topic 03 · layer 3

Conversation memory.

3

What it is

A buffer of prior user/assistant turns. Lets the agent resolve "what about 2023?" against the previous question. FIFO; capped at memory_size pairs.

How it's wired

InMemoryChatMessageHistory from langchain_core. The prompt template's MessagesPlaceholder(variable_name="chat_history") threads it through. _trim_memory trims FIFO.

Sidebar · Enable Conversation Memory · Memory Size

Topic 04 · 10 min

SQL AI Agent guardrails.

Context tells the agent what it should do. Guardrails decide what it's allowed to do.

Topic 04 · three guardrails

Three layers between LLM output and the DB.

Guardrail 01

Admin control — read-only

Only Select, With, Show, Describe. Everything else is blocked at the validator.

Guardrail 02

SQL validation

sqlglot parses first. Multi-statement input is blocked. Unparseable strings are conservatively blocked.

Guardrail 03

LIMIT enforcement

Every SELECT gets a LIMIT. Caps unbounded scans before they kill the workshop laptop.

Topic 04 · the defaults that matter

ValidationConfig.

Eight lines of safety. Defined in sql_ai_agent/sql_validator.py.

@dataclass
class ValidationConfig:
    read_only: bool = True
    max_limit: int = 10000
    enforce_limit: bool = True
    allowed_statements: list = field(
        default_factory=lambda: ["Select", "With", "Show", "Describe"]
    )

Topic 04 · why blocked = blocked

"

Safety beats correction.

When validation fails in read-only mode, SqlAgent.ask_question returns immediately. No retry. No fallback. Don't give the agent a second chance to ask for a destructive query.

Topic 04 · takeaway

Validate before you execute.

The validator is the only thing that knows the difference between "answer" and "modify".

read-only · parse first · enforce LIMIT

Model performance & evaluation.

Without an eval, model selection collapses to vibes.

Topic 05 · why eval matters

Define "working" before you pick.

The model card won't tell us how a model handles air_traffic. Pricing tier won't tell us either. Brand won't tell us at all.

What to measure

Success rate · latency · fix rate. Three numbers, three different questions.

Against what

A fixed test suite. The suite is the spec — pick the model after it exists.

How often

Every prompt change, every model bump. Drift is real.

Topic 05 · three rules for shipping

For the next time you pick a model.

1

Define the tests first.

The test suite is the spec. Pick the model after it exists, not before.

2

Always include a cheap and a local model.

The default isn't always the right choice. Local models hit 65–70% here, with full data privacy.

3

Re-run the eval whenever anything changes.

Prompt template, schema, skill file, model version. Drift is real. Production regressions are not cheap.

Topic 05 · takeaway

Eval surfaces what branding hides.

Pick the cheapest model that meets your bar.

success rate · latency · fix rate

Topic 06 · 8 min · recap

Best practices.

Five threads through everything we've covered.

Topic 06 · five practices

When you go ship one of these.

1

Context is a data-engineering discipline.

Curating distinct values and the skill file is engineering work. Treat it like a pipeline you own.

2

Skills compound.

Write the domain knowledge down once, version it. Every new edge-case rule benefits every future query.

3

Short-term and long-term memory serve different jobs.

In-process chat history for follow-ups; DB-backed Q&A logs for cross-session learning.

4

Measure, don't guess.

Re-run the eval whenever you change the prompt, the schema, the skill file, or the model.

5

Plan for the model to fail.

Hosted models rate-limit, time out, return un-parseable output. Configure a fallback. A local model is a strong one.
